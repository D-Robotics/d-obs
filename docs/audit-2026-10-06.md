# d-obs 全面诊断报告

审计日期：2026-10-06（Asia/Shanghai）
范围：服务端、公开 API、OTLP/设备/租户边界、告警 worker、工作台与门户体验、测试、构建、CI、依赖和本地启动体检。

## 结论

当前仓库没有证据显示存在已经确认的 P0，但还不具备“生产发布即放心”的条件。主要原因是公开写入面和多租户控制面仍有资源耗尽与并发边界，CI 没有把构建产物、鉴权、健康检查和真实数据库链路纳入门禁，依赖审计还有一个 high 漏洞。

本轮先处理了三个可直接修复的问题：

1. 生产环境未配置 `RDK_PUBLIC_OBSERVABILITY_API_TOKEN` 时，公开 API 拒绝任意动态 Bearer。
2. 模型池工作台响应剥离网关配置里的 `apiKey`。
3. 工作台总览返回空数据时进入可重试错误态，不再读取 `null.alerting`。

## P1：需要优先处理的问题

### 1. 依赖存在 high 漏洞

`package.json:38` 固定了 `undici 7.29.0`。`npm audit` 报告了 WebSocket 解压 DoS、响应拆分、TLS 连接选项丢失等问题，修复版本是 7.30.0。应升级 package 与 lockfile，随后跑完整测试、构建和网络客户端回归。

### 2. 公开写入 API 的资源配额不足

`server/public-api/public-observability-store.ts:259-260` 声明了 `MAX_SPANS_PER_RUN=256`，但追加路径每批最多截到 64 条后仍可无限重复写入；`persistAndStoreSpans` 直接把 span 放进 run 的 Map。实测同一 run 连续 6 批各 64 条，接受 384 条，超过声明上限。公开 spans、runs、feedback 等写入面也没有按 owner/IP/凭据的统一限流。

影响是内存、磁盘和数据库可被合法 token 持续消耗，还可能通过创建大量 run 驱逐其他 owner 的缓存。应在 store 层强制每 run/global quota，在路由层增加按凭据和 IP 的限速、并发上限和 429 回执。

### 3. 租户最后一个 owner 的保护只在进程内生效

`server/monitoring/tenant-members-store.ts:240-330` 使用进程内 Promise 队列串行化 owner 变更，代码注释也明确多实例会失效。多个 web 实例同时降权或移除 owner 时，可能都读到 owners=2，然后同时通过检查，造成租户无 owner。

应把读取和写入放进 PostgreSQL transaction，并对租户/成员行使用 `SELECT … FOR UPDATE`，或改成带数据库不变式的单条 `UPDATE/DELETE`。至少要增加双连接并发回归测试。

### 4. OTLP、探针、设备和租户注册的资源保护不一致

- `server/main.ts:109-186` 的 external probe、device heartbeat、command claim/ack 在身份解析发生于 `try` 之外，数据库异常时可能产生未处理 rejection 和悬挂请求。
- 租户注册、external probe 和设备心跳没有统一的 identity/IP 限速与并发上限。
- `server/observability/ai-ecosystem-grpc.ts:54-125` 的 gRPC 三信号入口只做凭据/TLS 检查，没有复用 HTTP ingest guard 的速率桶和消息并发限制。

应先统一 async route wrapper，再统一按凭据/IP 的速率、body/message 大小、并发和队列背压策略。

### 5. Grafana handoff 复用了管理员 token

`server/monitoring/observability-routes.ts:330-340` 把 `RDK_CREDITS_ADMIN_TOKEN` 原值放进 12 小时 `dobs_grafana_gate` Cookie。代理日志、浏览器 cookie、调试输出或 XSS 一旦拿到该 cookie，就等于拿到了全局管理员凭据。

应签发独立的短期 opaque/HMAC gate token，服务端只保存可验证的 gate 结果，绝不能复用 admin secret。

### 6. CI 没有覆盖构建、健康、鉴权和真实集成链路

`.github/workflows/ci.yml:18-30` 目前只跑 typecheck、unit tests 和 `/ops-observability` HTML 200。没有：

- `npm run build` 与 dist 启动冒烟；
- `/healthz`、`/readyz` 的状态码和结构化响应；
- 生产 fail-closed 鉴权、公开 API、OTLP 401/429；
- PostgreSQL、worker、trace/outbox、通知重试的集成测试；
- 浏览器级工作台交互测试；
- lint、依赖审计、覆盖率阈值或报告产物。

当前测试覆盖率不能代表生产链路覆盖率：`studio-alert-worker.ts` 只有 27.66% lines / 23.08% functions，`synthetic-probes.ts` 29.64% / 12.5%，`storage.ts` 43.2% / 2.04%。

### 7. 单测依赖真实外网，拖慢并增加 flaky 风险

`server/monitoring/alert-notification-channels.test.ts:78-129` 会向伪造的钉钉/Telegram URL 发起真实 fetch。一次 critical 路由测试约 32 秒，占完整测试套件绝大多数时间。

应给通知 transport 注入 fetch/client mock，单测只断言请求体、重试和错误归类；另设一个有明确短 timeout 的隔离网络集成测试。

## P2：需要排期的问题

### 可靠性和信息边界

- `server/monitoring/sso-relay.ts:455-508` 的登录限流 Map 没有定时 sweep 和硬容量上限，攻击者可以用大量不同账号名制造常驻 key。
- `server/monitoring/health-routes.ts:74-79` 的未鉴权 `/readyz` 会返回数据库错误字符串，可能泄露连接主机或拓扑。对外应只返回通用 reason，细节写日志。
- `server/monitoring/observability-signals-routes.ts:788-795` 的 MCP async handler 没有统一 catch；未来工具异常可能变成悬挂请求或 unhandled rejection。
- 当 `NODE_ENV` 为空或写成 `staging` 时，公开 API 仍允许动态 bearer。生产部署应显式设置 `NODE_ENV=production`，更稳妥的做法是启动时固定 token 缺失直接拒绝，或只在显式 development 开关下开放动态 token。
- `npm run doctor` 的 metrics-auth 在缺 token 时显示“✓”但 detail 仍是“configure …”，容易误读可选项与生产阻塞项。

### 代码结构

服务端渲染工作台由多个巨型模板字符串拼装，热点文件超过 1,000 行，页面脚本和状态模型的边界仍然很难独立测试。长期应按领域拆成可导入模块，并让 API response schema、DOM state 和权限矩阵成为独立契约。

## 体验与产品判断

### 已改善的部分

门户和工作台此前的高频摩擦已经处理：产品卡片有明确 CTA，目录弹窗支持搜索别名、焦点回收和 Escape，滚动导航高亮不再停在旧段，动画失败时页面仍可读；工作台移动端主导航更聚焦，告警中心栅格、暗色头部对比度、登录屏语义和初始错误态已改善。

### 仍需优化的部分

1. 工作台能力很多，用户的核心任务仍容易被“模块目录”打断。首屏应稳定围绕三条路径：判断影响、处置事故、查证据；模型池、数据库、学习闭环等低频控制面放在明确的次级入口。
2. Telemetry 头部、页面 meta、panel 错误态和 toast 都可能表达同一失败。应确定一个主状态容器，其余只补充上下文，减少重复噪声。
3. 真实数据库、租户成员、告警队列和链路数据没有可复现的浏览器 fixture，因此现在的视觉检查主要验证空态和错误态，不能证明“有数据时”的密度、排序、批量操作和下钻体验。
4. 门户和工作台的品牌、入口和登录语义仍是两套体验。应定义清晰的产品入口：门户负责发现与学习，工作台负责运营任务，并用一致的命名、状态色和权限解释连接起来。
5. 可访问性已有基础语义，但仍应补键盘完整路径、抽屉/命令面板焦点陷阱、动态状态播报和 320px 宽度的真实浏览器测试。
