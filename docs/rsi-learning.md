# 可验证进化实验

此模块将 [Towards AI That Improves Itself](https://lee1003-lee.github.io/Awesome-RSI-Research/assets/rsi-survey.pdf) 的 Proposal → Feedback → Optimization 思路落到一个可执行的工具失败归因实验。

入口：工作台 → 每日自我进化 → **可验证进化实验**。模块管理当前运营账号的失败证据、人工确认标签、冻结案例集和版本规则包。原有每日代码进化 worker 继续运行自己的候选治理。

当前已接入平台工具的失败回执：助手、MCP 和插件通过同一个 `executePlatformOperation` 执行器调用已注册操作，执行器在完成回执的 `finish` 路径触发后台采集。普通页面直接请求业务 HTTP 接口不经过该执行器，因此不属于本次采集范围。采集和规则归因不阻塞原调用结果，也不执行自动重试、处置或代码发布。

自动采集真实回执的路径已经实现，但目前用于验证两轮收益的数字仍来自受控夹具。`source: platform_operation` 表示通过平台工具回执采集，并不是生产收益的证明；新部署没有真实失败时应保持空状态。

## 完整流程

1. **观察失败**：工具失败回执自动进入“真实失败案例”，最初为 `unconfirmed`。成功请求、租户请求、只读请求，以及学习模块自身的操作不采集。相同操作模板、结构化错误输入和执行结果状态聚合为同一证据，更新次数与最近观察时间。
2. **人工确认**：操作者独立选择原因和 `frozen`、`adaptive`、`holdout` 分组，或排除无用观察。建议原因和已接受版本的预测都只作提示，不会自动变成确认标签。确认后的标签与分组保持固定；后续同类失败只更新观察次数和实际使用版本。
3. **冻结证据实验**：勾选已确认案例，三组至少各一条，创建实验。服务器从当前账号的收集箱构建案例，并冻结案例内容哈希及 `provenance`：案例 ID、证据 ID、指纹、已注册操作模板、首次观察时间、人工确认时间。不能重复引用证据，完全相同的归因输入不能跨评测组，即使操作模板不同也拒绝。
4. **提出候选**：只查看 `adaptive` 案例，从当前活动版本加载规则，提出一条新的通用规则，继承全部父版本规则。记录父版本、实际加载版本和提案证据。
5. **回放验证**：使用同一个解释器和预算，执行当前版本、候选版本、无继承对照。对照组每轮从初始版本重新执行一次相同提案算法。
6. **人工接受或拒绝**：只有历史、新增、留出三组均无回归，新增和留出均改善，且预算足够时，接受按钮才可用。服务器重新验证报告与候选、父版本、案例哈希绑定，客户端不能提交评分代替验证。
7. **下一轮继承**：再次提出候选时实际加载上一轮接受的规则包。第二轮可以在保留第一轮能力的基础上学习另一类失败，继续与从初始版本重学的对照组比较。
8. **显式用于新失败**：点击“用于新失败归因”才绑定该实验。绑定要求完整采集证据、全部案例来自人工确认、活动版本已通过回放并被接受，且没有待验证候选。此后新失败保存实际 `loopId`、`activeVersionId` 和预测原因；这证明该版本实际被读取使用，效果仍要由新观察的独立确认标签检验。合成实验和手工导入实验不能绑定。
9. **回退或停止使用**：可退回已接受祖先版本，保留候选、回放和决策记录。回退到已接受祖先后，新失败使用该祖先版本；回退到初始版本、出现待验证候选、绑定实验缺失或其依赖的采集证据被排除时，停止保存版本预测，仅保留失败观察和提示原因。也可点击“停止使用此实验”解除绑定。后续提案从回退后的活动版本开始。

手工录入案例和“创建合成示例”仍可用于实验演练；它们不带服务端采集证据，不能冒充真实回执或进入新失败绑定。

排除证据不会删除既有实验的来源快照或历史回放。当当前绑定实验依赖被排除的证据时，绑定状态变为 `evidence_excluded`，暂停新失败预测，避免继续使用已撤回的确认依据。需要用仍有效的确认案例创建新实验、完成验证和接受后再绑定。

## 从页面完成一次验证

1. 进入每日自我进化，刷新“真实失败案例”。没有观察时等待后续正常工具调用产生失败；页面不会为演示自动制造事故。
2. 结合业务事实确认原因，选择评测组，点击“确认案例”。不要因为提示写着“超时”就直接把它当作已确认根因。
3. 至少选择一条历史回放、一条新增弱点、一条独立留出，勾选“纳入实验”，填写名称并点击“用 N 条确认案例建立实验”。若要验证两轮继承，新增与留出组还需要覆盖两类可独立学习的错误。
4. 在同一实验依次点击“提出候选 → 回放验证 → 接受改进”，再重复一轮。查看三组准确率、改善与回归，以及“不继承对照”。若门禁未通过，保留证据并拒绝候选，不把失败报告转为接受依据。
5. 展开“版本、回放与决策记录”，核对父版本、加载版本、案例哈希和采集证据。接受后点击“用于新失败归因”。后续观察显示实际使用的已接受版本预测，再人工确认新观察，检查预测是否正确。
6. 需要恢复旧版本时选择祖先并点击“回退到此版本”；回退到初始版本后，页面显示绑定暂不可用，新失败观察仍会收集。

后台观察会改变收集箱修订号。若确认或绑定遇到 `409 rsi_inbox_stale_revision`，重新读取证据，核对最新状态后再提交；不要盲目重复原写请求。实验版本操作使用各自的实验修订号。

## 三组评测的职责

| 分组 | 用途 | 能否用于提案 |
| --- | --- | --- |
| `frozen` | 检查过去能解决的案例是否退步 | 否 |
| `adaptive` | 暴露新弱点，生成候选规则 | 是 |
| `holdout` | 检查对不同输入的迁移收益 | 否 |

不同分组不允许复制完全相同的输入。留出标签只进入验证器；同一套留出集反复用于接受决策仍可能形成间接选择偏差，因此实际使用应为新实验补充新的独立留出案例。第一版提供固定案例回放，不实现自动更新留出集的调度器。

## 示例如何体现继承

合成例子初始只识别 HTTP 401、404、400。第一轮从新增案例学会超时归因，第二轮继承超时规则后学会限流归因。两轮都用不同 HTTP 状态的留出案例检验规则迁移。第二轮的无继承对照仍从初始规则出发，只能重学第一条规则。

这些夹具结果用于验证此受限实验的版本持久化、实际加载和跨轮次积累。它们不代表生产故障识别率，也不足以证明改进器本身越来越强。修改目标是结构化归因规则，不涉及模型权重、平台权限或生产代码。新增的真实失败流程仍需要积累实际回执与人工确认，才可评价线上收益。

运行可复现的两轮示例：

```sh
node --import tsx tools/rsi-learning-demo.mjs --output /tmp/d-obs-rsi-demo.json
```

默认在临时目录创建示例账本；可用 `--state-dir DIR` 指定目录。无外部网络调用。

真实回执采集路径的受控夹具验收命令：

```sh
node --import tsx tools/rsi-real-evidence-smoke.mjs --state-dir /tmp/d-obs-rsi-evidence-smoke --output /tmp/d-obs-rsi-evidence-smoke.json
```

该脚本以 7 条预设失败夹具，经本机随机端口的 Express 工具回执、执行器 `finish` 和观察器进入收集箱；再按预设夹具标签调用确认接口，完成证据冻结、两轮继承、绑定和回退。绑定后的新夹具保存实际使用版本，但其确认标签仍为空；回退初始版本后再次观察，不再保存版本预测。脚本模拟人工确认流程，并未获得真实操作者对线上案例的确认。

清单明确标记 `source: fixture`、`productionDataUsed: false`、`productionImprovementClaimed: false` 和 `labelAuthority: preset_fixture_labels_submitted_through_operator_confirmation_http`。输出中的准确率只描述这次验收，不能当作线上真实故障指标。默认创建临时运行目录；指定 `--state-dir` 后仍在其下创建独立 UUID 子目录，`--output` 指定清单路径。所有 HTTP 请求仅使用 `127.0.0.1`，不调用外部服务或生产凭据。不要将验收目录配置为生产账本目录。

## HTTP 接口

前缀：`/api/ops/observability/evolution/learning`，契约 `rdk.rsi-learning.v1`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/capabilities` | 范围、预算和限制 |
| GET | `/evidence` | 当前账号失败观察、收集箱修订号、计数和绑定可用状态 |
| POST | `/evidence/:id/confirm` | `{expectedRevision,expectedReason,slice}` 人工确认原因与分组 |
| POST | `/evidence/:id/exclude` | `{expectedRevision}` 排除观察，不加入将来的实验 |
| POST | `/evidence/experiment` | `{expectedRevision,title,evidenceIds}` 用 3–200 条已确认证据建立冻结实验 |
| POST | `/binding` | `{expectedRevision,loopId}` 显式绑定已接受证据实验；`loopId:null` 解除绑定 |
| GET | `/loops` | 当前账号实验与累计接受/继承轮数 |
| GET | `/loops/:id` | 案例、版本、回放、决策 |
| GET | `/loops/:id/classify` | 用活动规则归因，可传 `httpStatus`、`errorCode` |
| POST | `/loops` | `{title,cases,rules?}` 创建冻结案例集 |
| POST | `/demo` | `{}` 显式创建合成示例 |
| POST | `/loops/:id/propose` | 生成候选 |
| POST | `/loops/:id/replay` | 执行三组回放 |
| POST | `/loops/:id/accept` | 接受经过验证的候选 |
| POST | `/loops/:id/reject` | 拒绝候选 |
| POST | `/loops/:id/rollback` | 回退到祖先版本 |

确认、排除、证据实验创建和绑定请求的 `expectedRevision` 来自 `GET /evidence` 的 `overview.revision`，是整个账号收集箱的修订号。已有实验版本操作的 `expectedRevision` 来自实验的 `loop.revision`；回退另带 `{versionId}`。首次空收集箱修订号为 1，每次观察、确认、排除和绑定都会增加。

写入复用运营动作和同源检查，拒绝只读模式。权限来自服务端运营账号身份；请求不能提供其他账号 owner，其他账号的证据和实验返回不存在。助手可读取实验，写动作通过实验页面或显式 API 执行。

`POST /evidence/experiment` 仅接收证据 ID，由服务器读取本账号已确认记录并生成 `source: operator` 案例与 `provenance`。普通 `POST /loops` 的严格 schema 拒绝提交 `provenance`；自行填写 `source: operator` 的手工案例不等同于采集证据，不能通过绑定资格检查。不存在供客户端直接写入失败回执的采集接口。

案例格式：

```json
{
  "id": "timeout-new-1",
  "slice": "adaptive",
  "input": {"httpStatus": 504, "errorCode": "ETIMEDOUT"},
  "expectedReason": "timeout",
  "source": "operator"
}
```

支持原因：`timeout`、`rate_limited`、`auth_denied`、`not_found`、`upstream_unavailable`、`connection_refused`、`invalid_input`、`unknown`。

## 采集边界与执行结果

观察记录保存证据 UUID、首次与最近观察时间、聚合次数、指纹、操作模板、`input`、`executionOutcome`、提示原因、人工标签，以及实际规则预测。指纹只由操作模板、有限错误输入和执行结果状态确定。操作 ID 必须是已审查注册的模板，例如 `GET /api/ops/observability/objects/:objectId`，不会保存实例化的资源 ID 或查询参数。

`input` 仅包含 HTTP 状态码和固定错误码：`ETIMEDOUT`、`ECONNREFUSED`、`EAI_AGAIN`、`EINVAL`、`AUTH_DENIED`、`RATE_LIMITED`、`NOT_FOUND`、`UPSTREAM_UNAVAILABLE`。观察器只读取回执 `data.error` 的单个自身数据字段，严格匹配固定错误码或有限平台机器错误映射；未知文本丢弃，不从自然语言消息中提取内容。不会保存原始错误消息、回执正文、请求 body、工具实参、提示词、身份或凭据。用于文件隔离的 owner 只存 SHA-256 摘要。

HTTP 200 也可能承载 `ok:false` 的失败回执。执行器已经判定回执失败时，内部观察器通过严格的 `receiptFailure:true` 标志保留该状态码；未知机器错误仍不保存原文，提示原因为 `unknown`。没有这个可信标志、没有固定错误码的普通 HTTP 200，或完全没有错误特征的空输入仍被拒绝。该标志没有客户端写入入口，也不会成为原因标签；这类观察仍须人工确认才能加入实验。

`executionOutcome` 与错误原因是两件事：只读操作的失败回执标记为 `failed`，变更操作的失败回执保守标记为 `unknown`。例如一次创建操作超时，可以确认请求错误为 `timeout`，但不能据此断定服务端没有完成创建。规则学习仅改善请求错误归因，不能成为自动重试依据。

采集为后台尽力完成，同一观察器最多 32 个挂起任务；过载、写锁繁忙或持久化失败时不改变原业务回执，因此收集箱不承诺涵盖每一次失败。

## 持久化与限额

| 数据 | 配置与默认目录 | 单账号限制 |
| --- | --- | --- |
| 失败收集箱 | `RDK_RSI_FAILURE_STATE_DIR`；`~/.local/state/d-obs/rsi-failures` | 500 条聚合观察，文件最多 2 MiB |
| 进化证据账本 | `RDK_RSI_STATE_DIR`；`~/.local/state/d-obs/rsi` | 50 个实验；每个实验 200 条案例、100 个版本、100 次回放、300 条决策；文件最多 32 MiB |

收集箱达到 500 条后，新指纹观察淘汰最近观察时间最早的未确认或已排除记录，保留已确认案例；全部记录均已确认时拒绝新增，返回 `rsi_inbox_record_limit`。重复指纹仍可聚合已有观察。实验建立后保存自己的案例和来源快照，后续观察更新不会改写已冻结的案例。

两个目录都按运营身份摘要保存 `<ownerHash>.json`，目录权限为 `0700`，文件权限为 `0600`。状态带内容校验哈希；写入先写私有临时文件并同步，再原子 rename 和同步目录。并发写入使用进程内队列及 `<ownerHash>.guard`、`<ownerHash>.lock`；完整临时锁记录写完并同步后通过 `fs.link` 排他发布，避免其他进程读到半条锁记录。写锁等待上限为 3 秒，忙时返回 `409`；身份存储损坏和不安全路径拒绝操作。

备份应包含两个目录。部署副本需要共享支持这些原子文件操作的同一可靠文件系统；当前实现是本地文件账本，不提供分布式数据库协调。不要为修复损坏静默清空历史证据。
